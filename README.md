# Бинарная классификация: прогнозирование повторной госпитализации пациентов

Проект по бинарной классификации на табличных данных. Цель — предсказать, произойдёт ли повторная госпитализация пациента в течение 30 дней.

## Данные

Исходный датасет:

- 101 766 наблюдений;
- 50 исходных признаков;
- 71 518 уникальных пациентов;
- числовые и категориальные признаки;
- большое количество пропусков;
- сотни кодов диагнозов;
- выраженный дисбаланс классов.

Целевая переменная `readmitted` была преобразована в бинарную:

- `1` — повторная госпитализация менее чем через 30 дней;
- `0` — госпитализация позже 30 дней или её отсутствие.

Положительный класс составляет около 11% данных.

## Подготовка данных

Один пациент может встречаться в датасете несколько раз, поэтому обычный случайный split мог привести к попаданию разных госпитализаций одного человека одновременно в train и test.

Разделение проводилось по `patient_nbr` с помощью `GroupShuffleSplit`. Для подбора моделей использовался `StratifiedGroupKFold`.

Для пропусков использовались разные стратегии в зависимости от признака: удаление почти пустых столбцов, отдельные категории `Unknown` / `Missing`.

Категориальные признаки кодировались с помощью One-Hot Encoding и Ordinal Encoding. Кодировщики обучались на train.

Диагнозы `diag_1`, `diag_2`, `diag_3` были объединены в более крупные группы. Дополнительно создавались признаки, связанные с хроническими заболеваниями, инфекциями и гипертензией.

## Feature engineering

Было создано несколько вариантов наборов признаков.

Дополнительно использовались:

- `total_visits` — общее количество предыдущих обращений;
- `drug_intensity` — агрегированный признак лекарственной терапии;
- `activity` — интенсивность лечения;
- бинарные признаки длительного пребывания и большого количества визитов;
- взаимодействия признаков, например `age_num_inpatient` и `longstay_procedures`.

Сравнение разных наборов показало, что увеличение количества engineered features не всегда улучшает результат.

## Работа с дисбалансом

Сравнивались `class_weight` и `SMOTETomek`.

`SMOTETomek` не показал стабильного преимущества, поэтому финальная модель использует взвешивание классов без oversampling.

## Модели

Сравнивались:

- Logistic Regression;
- Decision Tree;
- Random Forest.

Гиперпараметры подбирались через `GridSearchCV`.

Основные метрики:

- precision;
- recall;
- F1-score;
- ROC-AUC.

Отдельно рассматривались модели, подобранные по F1 и recall.

## Валидация

Схема работы:

```text
данные
  ↓
group split по patient_nbr
  ↓
train / validation / test
  ↓
StratifiedGroupKFold + GridSearchCV
  ↓
выбор модели
  ↓
подбор threshold на validation
  ↓
финальная оценка на test

## Результаты

Лучшие результаты на validation среди рассмотренных вариантов:

| Модель | Набор | F1 класса 1 | Recall класса 1 |
|---|---|---:|---:|
| Logistic Regression | X21 | 0.243 | 0.436 |
| Decision Tree, F1 | X22 | 0.222 | 0.555 |
| Decision Tree, recall | X23 | 0.199 | 0.601 |
| Random Forest | **X25** | **0.245** | **0.498** |

Для Decision Tree полный перебор всех наборов признаков не проводился из-за большого времени расчёта.

В некоторых экспериментах модели показывали очень высокий recall, но при этом почти всё относили к положительному классу. Поэтому модель выбиралась не только по recall, но и с учётом F1 и precision.

## Финальная модель

Финальной моделью выбран **Random Forest на наборе X25**.

```python
RandomForestClassifier(
    n_estimators=25,
    max_depth=10,
    max_features="sqrt",
    min_samples_leaf=4,
    min_samples_split=2,
    class_weight="balanced_subsample",
    random_state=42
)

На validation:

- F1 класса 1 — **0.245**
- Recall — **0.498**
- Precision — **0.163**

Дополнительно на validation подбирался classification threshold с учётом условной стоимости ошибок. Выбранный порог — **0.46**.

## Результат на test

После изменения threshold модель обнаруживает около 74% положительных случаев, но при этом растёт количество False Positive. ROC-AUC показывает, что разделяющая способность модели остаётся ограниченной.
