# Бинарная классификация: прогнозирование повторной госпитализации пациентов

Проект по бинарной классификации на крупном неоднородном табличном датасете. Цель — оценить риск **повторной госпитализации пациента в течение 30 дней** после текущего эпизода лечения.

Основной акцент проекта — не только на обучении моделей, но и на корректной работе с повторными наблюдениями одного пациента, выраженным дисбалансом классов, большим количеством категориальных признаков и пропусков, feature engineering, cross-validation, подборе гиперпараметров и анализе компромисса между precision и recall.

## Данные и постановка задачи

Исходный датасет содержит:

- **101 766 наблюдений**;
- **50 исходных признаков**;
- **71 518 уникальных пациентов**;
- **16 773 пациента** имеют несколько госпитализаций;
- числовые и категориальные признаки;
- сотни различных кодов диагнозов;
- признаки с большим количеством пропусков;
- выраженный дисбаланс целевой переменной.

Целевая переменная `readmitted` преобразована в бинарную:

- `1` — повторная госпитализация произошла **менее чем через 30 дней**;
- `0` — повторная госпитализация произошла позже 30 дней либо отсутствовала.

Доля положительного класса составляет около **11%**, поэтому accuracy сама по себе не является достаточной метрикой качества.

## Основные сложности задачи

### Повторные наблюдения одного пациента

Один пациент может встречаться в датасете несколько раз. Обычный случайный split мог бы поместить разные госпитализации одного человека одновременно в train и test и сделать оценку качества слишком оптимистичной.

Поэтому разделение выполнено **по `patient_nbr`** с помощью `GroupShuffleSplit`.

Проверено отсутствие пересечения пациентов между train, validation и test.

Для подбора моделей используется **5-fold `StratifiedGroupKFold`**, который одновременно сохраняет группировку по пациентам и учитывает дисбаланс классов.

### Пропуски и категориальные признаки

В данных присутствуют признаки с очень разной долей пропусков — от единичных значений до более 90%.

В зависимости от смысла признака использовались разные стратегии:

- удаление практически пустых и малоинформативных столбцов;
- отдельная категория `Unknown` / `Missing`;
- сохранение отсутствия лабораторного результата как отдельного состояния;
- One-Hot Encoding номинальных категориальных признаков;
- Ordinal Encoding признаков, для которых задан естественный порядок.

Обучаемые кодировщики категориальных признаков fit-ятся на train и затем применяются к validation/test с `handle_unknown='ignore'`.

### Диагнозы

Исходные `diag_1`, `diag_2`, `diag_3` содержат сотни различных кодов.

Чтобы снизить размерность и сохранить смысловую информацию, диагнозы сгруппированы по укрупнённым категориям, после чего преобразованы с помощью One-Hot Encoding.

Дополнительно созданы признаки:

- наличие гипертензии;
- наличие инфекционного заболевания;
- количество хронических состояний.

### Дисбаланс классов

Положительный класс встречается примерно в 8 раз реже отрицательного.

В экспериментальной части сравнивались:

- `class_weight`;
- `SMOTETomek`;
- модели без sampling;
- модели с sampling внутри training pipeline.

`SMOTETomek` не дал устойчивого преимущества, поэтому финальная модель использует **взвешивание классов без oversampling**.

## Feature engineering

Было построено несколько альтернативных пространств признаков, чтобы проверить, насколько усложнение представления данных влияет на качество.

### Агрегированные признаки

- `total_visits` — суммарное число предыдущих outpatient / emergency / inpatient обращений;
- `drug_intensity` — агрегированная характеристика лекарственной терапии;
- `activity` — агрегированная характеристика интенсивности лечения.

### Бинарные индикаторы

- `long_stay`;
- `long_drug_intensity`;
- `long_total_visits`.

### Взаимодействия признаков

- `age_num_inpatient`;
- `gender_diabetes`;
- `longstay_procedures`;
- `infection_time`.

В результате были сформированы несколько вариантов датасета: от более полного набора исходных признаков до компактных наборов с агрегациями, бинарными индикаторами и взаимодействиями.

Эксперименты показали, что **добавление большего количества engineered features не гарантирует улучшения качества** — результат зависит от комбинации признаков и выбранного алгоритма.

## Модели

В проекте сравнивались три семейства моделей:

- **Logistic Regression**;
- **Decision Tree**;
- **Random Forest**.

Для каждой модели выполнялся подбор гиперпараметров через `GridSearchCV`.

Основные метрики:

- precision класса 1;
- recall класса 1;
- F1-score класса 1;
- ROC-AUC.

Отдельно рассматривались конфигурации, оптимизированные по **F1** и по **recall**.

Для Logistic Regression масштабирование выполняется внутри pipeline, чтобы preprocessing корректно участвовал в cross-validation.

## Схема валидации

```text
исходные данные
      |
      v
group split по patient_nbr
      |
      +----------+------------+
      |          |            |
    train   validation       test
      |
      v

      |
      v

      |
      v
выбор модели и признаков
      |
      v

      |
      v
выбор финальной модели
      |
      v

      |
      v
однократная финальная оценка на test
```

`test` не используется для подбора набора признаков, гиперпараметров или classification threshold.

## Результаты сравнения

Лучшие validation-результаты среди рассмотренных конфигураций:

| Модель | Набор | F1 класса 1 | Recall класса 1 |
|---|---:|---:|---:|
| Logistic Regression, оптимизация F1 | X21 | 0.243 | 0.436 |
| Decision Tree, оптимизация F1 | X22 | 0.222 | 0.555 |
| Decision Tree, оптимизация recall | X23 | 0.199 | 0.601 |
| Random Forest | **X25** | **0.245** | **0.498** |

Для Decision Tree из-за высокой вычислительной стоимости полного GridSearch проверялось ограниченное подмножество наиболее перспективных feature sets.

Отдельно встречались модели с формально очень высоким recall, но почти нулевой полезностью: модель может начать относить практически все объекты к классу `1`. Поэтому выбор модели выполнялся не по максимальному recall любой ценой, а с учётом F1 и precision.

## Финальная модель

По F1 на validation была выбрана:

**Random Forest, набор X25**

Параметры:

```python
RandomForestClassifier(
    n_estimators=25,
    max_depth=10,
    max_features="sqrt",
    min_samples_leaf=4,
    min_samples_split=2,
    class_weight="balanced_subsample",
    random_state=42
)
```

Набор X25 включает категориальные и клинические признаки после preprocessing, дополнительные флаги, бинарные индикаторы и взаимодействия признаков.

На validation при стандартном пороге модель показала:

- **F1 класса 1: 0.245**
- **Recall класса 1: 0.498**
- **Precision класса 1: 0.163**

## Подбор classification threshold

Для отдельного эксперимента задана условная стоимость ошибок:

- False Positive — `1 000`;
- False Negative — `10 000`.

Эти значения используются **только как иллюстративная функция стоимости** и не являются реальной оценкой медицинских или экономических последствий.

Порог подбирался исключительно на validation.

Оптимальный порог: **0.46**.

Снижение threshold увеличивает число обнаруженных повторных госпитализаций, но одновременно повышает число ложноположительных прогнозов.

## Интерпретация модели

Для Random Forest анализируется встроенная `feature_importances_` и выполняется дополнительная интерпретация с помощью **SHAP**.

Среди наиболее важных признаков по Random Forest feature importance:

Наиболее заметную роль играют признаки, связанные с предыдущими госпитализациями и обращениями, возрастом, характеристиками текущей госпитализации и интенсивностью лечения.

SHAP используется для оценки вклада признаков в предсказания модели. Важно: feature importance и SHAP **не доказывают причинно-следственную связь**.

## Ограничения и дальнейшая работа

Текущий результат имеет несколько ограничений:

- ROC-AUC остаётся умеренно низким;
- precision положительного класса низкий;
- после threshold tuning возникает большое число False Positive;
- условная функция стоимости не основана на реальных экономических данных;
- для Decision Tree полный перебор всех feature sets не проводился из-за высокой вычислительной стоимости;
- для дальнейшего улучшения необходимы более сильные модели и дополнительная работа с признаками и данными.

Возможные следующие шаги:

- CatBoost / LightGBM / XGBoost;
- Balanced Random Forest;
- анализ False Positive и False Negative;
- probability calibration;
- дополнительная оптимизация threshold;
- более глубокий feature engineering;
- расширение обучающей выборки;
- проверка устойчивости на независимом датасете.
